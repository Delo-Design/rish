# Первый этап переписывания clonesite.sh для rish2

## Статус

Первый этап считается завершенным.

Новая реализация клонирования сайта перенесена в:

```text
scripts/clonesite.sh
```

Скрипт подключается из Midnight Commander menu через `templates/mc.menu`.
В `ri.sh` пункты клонирования удалены из меню управления сервером.

## Что было сделано

### Точка входа

Добавлен пункт меню:

```text
Клонирование сайта
```

Он расположен в `templates/mc.menu` после бэкапов и запускает:

```bash
bash /root/rish/scripts/clonesite.sh
```

При запуске скрипт показывает меню:

- клонирование сайта;
- клонирование только базы данных сайта;
- выход.

После завершения выбранного действия скрипт ожидает нажатия Enter.

### Основной сценарий

Первый этап поддерживает перенос одного сайта с удаленного сервера на текущий сервер.

Сценарий:

1. выбрать SSH host источника;
2. проверить SSH-доступ прямым SSH/TCP-подключением, без `ping`;
3. получить список сайтов источника из `/var/www/<user>/www/<site>`;
4. выбрать сайт;
5. определить параметры источника:
   - сайт и пользователь;
   - `site_root`;
   - относительный `DocumentRoot`;
   - PHP label;
   - полную версию PHP, если доступна;
   - наличие базы данных;
   - SSL-ссылки в vhost, если есть;
6. выбрать локального пользователя;
7. подтвердить имя целевого сайта;
8. выбрать PHP, если такая же версия не установлена локально;
9. создать сайт через `create_site_core` или использовать существующий vhost по безопасной политике;
10. перенести файлы в `site_root`;
11. перенести базу данных, если она есть;
12. поправить CMS config, если определена Joomla.

## Принятые решения

### scripts/

Новый скрипт живет в:

```text
scripts/clonesite.sh
```

Общие функции вынесены в:

```text
scripts/site_helpers.sh
```

`archive.sh` теперь также использует `scripts/site_helpers.sh`, чтобы логика настройки Joomla config и импорта базы не расходилась.

### create_site_core

`scripts/clonesite.sh` не генерирует Apache vhost вручную.

Для нового сайта используется:

```bash
create_site_core "$site_name" "$site_path" "$php_version" "$document_root" "$php_mode" "$restart_php_fpm" "$reload_apache" "$update_hotlist"
```

Это сохраняет единое место создания сайта, vhost и PHP-FPM pool.

### site_root и DocumentRoot

Файлы сайта всегда переносятся в `site_root`, а не в `DocumentRoot`.

Пример:

```text
site_root:    /var/www/user/www/example.com
DocumentRoot: /var/www/user/www/example.com/public
```

В таком случае перенос идет в:

```text
/var/www/user/www/example.com
```

`DocumentRoot` источника должен быть равен `site_root` или быть относительным подкаталогом внутри `site_root`.
Внешний абсолютный путь и `..` не поддерживаются.

### SSH

Проверка доступа к источнику выполняется через SSH/TCP:

```bash
ssh -q -o BatchMode=yes -o StrictHostKeyChecking=no -o ConnectTimeout=5 "$host" 'exit 0'
```

`ping` не используется.

### Файлы сайта

Файлы переносятся tar-потоком через SSH со сжатием:

```text
remote tar -> ssh -C -> local tar
```

Временный tar-архив на источнике или цели не создается.

Перед переносом всегда выводится размер исходного сайта.

Если на целевом сервере установлен `pv`, показывается прогресс передачи.
Если `pv` не установлен, скрипт явно сообщает, что прогресс показан не будет.

Прогресс через `pv -s` считается по размеру файлов `du -sb`.
Из-за tar-overhead он может быть примерным и иногда показывать больше 100%.

### База данных

Соглашение rish: база сайта называется как домен сайта.

`MYSQLPASS` не используется.

Дамп создается на источнике через:

```text
mariadb-dump | sed | gzip
```

Команда выполняется через `bash -o pipefail -c`, чтобы ошибка `mariadb-dump` не маскировалась успешным `gzip`.

Локально создается база с именем целевого сайта, пользователю выдаются права, затем импортируется `.sql.gz`.

Импорт поверх существующей базы допустим, потому что дампы MariaDB обычно содержат `DROP IF EXISTS`.

### Политика существующего целевого сайта

Если целевой vhost уже существует, перенос разрешен только если:

- vhost существует именно для целевого имени сайта;
- `DocumentRoot` совпадает с ожидаемым путем;
- `site_root` отсутствует или не содержит файлов/симлинков.

Если `site_root` отсутствует, он создается.

Если в `site_root` уже есть файлы или симлинки, перенос останавливается.
Пустые вложенные директории не считаются содержимым сайта и не блокируют перенос.

Перезапись существующих файлов сайта в первом этапе не поддерживается.

### PHP

Если PHP-версия источника установлена на текущем сервере, она выбирается автоматически.

Если такой версии нет, пользователь выбирает одну из установленных локально.

В визуальном summary показывается:

```text
PHP: php82 / 8.2.31
```

Если полную версию определить не удалось, показывается только label, например:

```text
PHP: php82
```

### Визуальный summary

Для переноса сайта выводятся две рамки рядом:

```text
Источник --------> Цель
```

В рамках показываются только основные характеристики:

- сайт и пользователь;
- `DocumentRoot`;
- PHP;
- база данных.

Имя сайта подсвечивается зеленым.
Путь к `site_root` в рамке не показывается, чтобы не перегружать интерфейс.

### SSL

Если на источнике найдены SSL-ссылки в vhost, скрипт сообщает об этом.

Автоматический перенос SSL в первом этапе не выполняется.

Для server -> server сценария это остается отдельным вопросом следующего этапа.

### Timezone в ri.sh

В `ri.sh` при установке часового пояса добавлен выбор:

- Москва (`Europe/Moscow`);
- Астана, Казахстан (`Asia/Almaty`);
- оставить текущий часовой пояс с показом текущего значения в скобках.

## Проверки

Синтаксическая проверка проходит:

```bash
bash -n scripts/clonesite.sh scripts/site_helpers.sh archive.sh ri.sh
```

## Что не входит в первый этап

Не реализовано:

- автоматический перенос SSL-сертификатов;
- выпуск self-signed SSL для локального сайта;
- исключения папок при переносе файлов;
- dry-run;
- overwrite существующего сайта;
- массовая миграция сервера;
- клонирование пользователя целиком;
- non-interactive/core API для переиспользования в массовых сценариях.

## Следующий архитектурный шаг: interactive + core

Перед сценарием клонирования пользователя нужно разделить клонирование сайта на два слоя.

### Interactive/orchestrator

Интерактивный слой:

- показывает меню через `vertical_menu`;
- задает вопросы через `read`;
- выбирает сервер, сайт, пользователя, PHP и режим PHP;
- рисует summary-рамки;
- делает `clear`;
- ожидает Enter после завершения.

Этот слой нужен для ручного запуска из `mc.menu`.

### Core/non-interactive

Core-слой должен получать готовые параметры и не задавать вопросов.

Он не должен:

- вызывать `vertical_menu`;
- читать пользовательский ввод;
- очищать экран;
- ждать Enter.

Он должен выполнять:

- проверку источника и цели;
- создание сайта через `create_site_core` или безопасный reuse;
- перенос файлов;
- перенос базы;
- настройку CMS config;
- понятный лог выполнения.

Core не обязан быть полностью silent.
Для клонирования пользователя и массовой миграции нужны сообщения и логи, но без интерактивных вопросов.

Возможная будущая структура:

```bash
clone_site_interactive
  # собирает параметры
  # вызывает clone_site_core

clone_site_core
  # получает готовые параметры
  # выполняет перенос
```

Возможные управляющие флаги:

```bash
CLONE_INTERACTIVE=0
CLONE_VERBOSE=1
CLONE_ASSUME_YES=1
CLONE_COPY_FILES=1
CLONE_COPY_DB=1
```

Сигнатуру `clone_site_core` лучше проектировать осторожно.
У клонирования уже много параметров: источник, цель, пользователи, `DocumentRoot`, PHP, БД, SSL, политики, исключения.
В shell слишком длинная позиционная сигнатура быстро станет неудобной.
